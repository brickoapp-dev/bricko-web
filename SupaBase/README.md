# Supabase — esquema y migraciones

Este directorio versiona los cambios de backend (base de datos) que antes se
hacían a mano por el dashboard. El proyecto es `wkyqetwyswocrohayiss`.

## ⚠️ Este directorio no es 100% fiel a producción

Al inspeccionar el esquema real (2026-08-13, por el SQL editor, ver
`…_move_dni_to_private_table.sql` y `…_request_images.sql`) se confirmó que
**`…_pro_profile_fields.sql` nunca se aplicó** — `profiles` no tenía
`username/address/province` y `professionals` nunca tuvo
`dni_number/dni_front_url/dni_back_url` — mientras que migraciones
posteriores (`…_professional_profile_fields.sql`, `…_storage_buckets.sql`)
sí. Además, producción tiene columnas y buckets que no vinieron de ningún
archivo de acá (`requests.fotos`, `requests.ciudad/provincia`, tablas
`messages`/`payments`/`pro_applications`, buckets `request-photos` y
`solicitudes` creados a mano). Si vas a escribir una migración nueva,
**no asumas que el estado acá descripto es el real** — confirmá contra la
base antes de escribir `ALTER`/`DROP`.

## Migraciones (`migrations/`)

Listadas en orden. "Aplicada" refleja lo confirmado contra producción, no
solo que el archivo exista acá.

Actualiza `handle_new_user` para poblar los campos nuevos de `profiles` y crear la fila de `professionals` sin tocar datos de DNI. |
| `…_request_images.sql` | **Aplicada 2026-08-13.** No agrega columna — `requests.fotos text[]` ya existía. Encontró DOS intentos previos incompletos hechos a mano: bucket `request-photos` (privado, folder=uploader, un profesional no podía ver fotos ajenas) y bucket `solicitudes` (público, cualquiera veía cualquier foto). | `…_equipo_link_participantes.sql` | **Aplicada 2026-08-26.** `hito_participantes` (equipo asignado a un hito de una obra puntual) no tenía ninguna relación con `pro_equipo` (directorio "Mi equipo" del profesional) — el formulario de participantes en `pro-preobra.html` era texto libre, sin poder elegir a alguien ya cargado en el equipo. | `…_plan_hitos_versiones.sql` | **Aplicada 2026-09-02.** Plan por hitos [22]-[27],[31] con versionado (T4), mismo patrón que `contrato_versiones`. FROM authenticated`). |

| `…_reabrir_invalida_contrato_firmado.sql` | **Aplicada 2026-09-02.** Fix encontrado al verificar el checklist de aceptación del contrato: `plan_hitos_reabrir()` invalidaba `plan_hitos_versiones` pero nunca tocaba `contrato_versiones` -- un contrato ya FIRMADO por las dos partes sobrevivía intacto aunque se reabriera y editara el plan de hitos después, contradiciendo el aviso explícito que pro-preobra.js ya le muestra al usuario antes de reabrir ("el contrato firmado va a quedar invalidado"). Ahora invalida cualquier versión activa (incluida `firmado`) al reabrir. `contrato_invalidar_si_cambio()` sigue sin tocar `firmado` a propósito -- corre pasivamente en cada carga de pantalla sin aviso al usuario, y no debe invalidar un contrato legal firmado por un cambio incidental en otro dato; reabrir es, en cambio, una acción explícita con aviso previo. |
| `…_cuit_checksum_constraint.sql` | **Aplicada 2026-09-02.** Fix encontrado al verificar el checklist: `profiles`/`professional_verification` solo chequeaban formato de 11 dígitos para `cuit`, no el dígito verificador -- client-perfil.js/properfil.js validan el checksum módulo 11 y frenan el guardado, pero como esas tablas se actualizan por policy UPDATE normal (no por RPC), un POST directo a PostgREST evitando la UI podía persistir un CUIT con dígito verificador inválido. Agrega `es_cuit_valido()` (mismo algoritmo que `validarCuit()` en JS) y lo usa en el CHECK constraint de ambas tablas. |
| `…_carpeta_publica_loguea_intentos_invalidos.sql` | **Aplicada 2026-09-02.** Fix encontrado al verificar el checklist ("QR revocado o vencido -> sin acceso, y el intento queda registrado"): `carpeta_publica()` hacía `RETURN NULL` apenas detectaba un token revocado/vencido, antes del INSERT en `qr_accesos` -- el intento nunca quedaba logueado. Se mueve el registro del intento antes del chequeo de validez: todo intento sobre un token que existe en `qr_tokens` queda registrado exista o no sea válido, y solo se devuelven datos si lo es. Un token que ni siquiera existe no puede loguearse (`qr_accesos.token` tiene FK a `qr_tokens(token)`) y tampoco hay nada que asociarle. |

## Paso manual pendiente (no se puede hacer por SQL)

- **Activar "Leaked password protection"** en el panel: Authentication → Policies /
  Password. Chequea contraseñas contra HaveIBeenPwned. Lo marca el linter de
  seguridad de Supabase.

## Cómo se aplicaron

La mayoría vía el MCP de Supabase (`apply_migration`) contra el proyecto de
producción. `…_move_dni_to_private_table.sql` y `…_request_images.sql`
(2026-08-13) se aplicaron a mano por el SQL editor del dashboard porque el
MCP devolvía error de autenticación contra la base — por eso convenía
verificar el esquema real antes de escribir esas dos (ver advertencia
arriba). Si en el futuro se usa el CLI de Supabase, estos archivos ya sirven
como historial reproducible del esquema — pero confirmá contra la base antes
de asumir que algo de acá está aplicado.
